## 공용 스킬로 두 에이전트 연결하기

두 에이전트는 같은 스킬 파일을 공유합니다. `~/.claude/skills/collab`과 `~/.gemini/config/skills/collab`이 모두 하나의 설정 저장소를 가리키는 심볼릭 링크로 묶여 있어, 한쪽에서 규칙을 고치면 양쪽에 곧바로 반영됩니다.

<CollabLoopDiagram />

<details>
<summary>세션 파일 구조와 실행 명령 펼쳐 보기</summary>

- 저장 위치: 진행 중 `~/.collab/sessions/`, 종료 `~/.collab/archive/`
- 세션 필드: `initiator`, `workdir`, `request`, `inherited`(이어받은 이전 결론), `entries`(`opinion` / `reply` / `note`), `conclusion`
- 명령: `start`, `send`, `note`, `end`, `archive [--here]`, `resume`, `purge [--match] [--sessions] [--yes]`, `status`
- 상대 호출은 9분 타임아웃으로 동작하며, 호출에 실패하면 해당 의견은 기록하지 않습니다. 이때만 CLI 설치·로그인·스킬 경로 같은 사전 요구사항을 진단해 오류 메시지에 덧붙입니다.

</details>

재미있었던 점은 이 스킬 자체도 두 에이전트의 협업으로 다듬어졌다는 것입니다. `antigravity-config` 저장소의 `collab` 스킬 커밋 **12개**는 모두 첫날(11월 18일)에 집중되어 있고, 그날 돌린 세션 **18건 중 10건**이 스킬 설계와 동작 점검에 쓰였습니다.

처음에는 보고 형식을 `의견 요약 / 인정 / 반박 / 현재 입장` 네 칸으로 나누어 두었는데, 막상 써 보니 보고서처럼 딱딱했습니다. 동의하는 상황에서도 반박 칸을 억지로 채워야 했고, 발의자가 요약하는 과정에서 응답자의 원문이 가려지는 문제도 있었습니다. 양측 의견을 모아 `[상대] 원문 + [나] 답변` 형태의 대화형으로 바꾸고 나서야 흐름이 한눈에 들어왔습니다.

내부 구현도 초기 Bash 스크립트에서 Python과 JSON 기반으로 옮겼습니다. Gemini가 초안을 검토하면서 호출 실패 시 기록이 꼬이거나 무한 대기에 빠지고, 구분 마커가 오작동할 위험을 짚어 주었기 때문입니다. 실제로 굴려 보며 부딪힌 자잘한 함정도 첫날 대부분 손봤습니다. 타임아웃이 걸렸을 때 하위 프로세스가 남지 않도록 프로세스 그룹 단위로 종료하게 고쳤고, 응답자가 실행 모드에서 주입된 plan 지침에 끌려가 검증 대신 계획만 세우거나 전역 규칙 때문에 나에게 질문하려다 멈추는 문제도 응답자 규칙으로 막았습니다. 매 라운드 전체 기록이 전달되는 구조라 토큰 비용이 쌓이는 점은 `경로:줄` 근거 표기와 인사·재진술 금지 규칙으로 줄였습니다.

반대로 검토 끝에 접은 아이디어도 있습니다. 매번 전체 기록을 넘기는 대신 전달할 범위를 발의자가 고르게 하자는 제안이었는데, 두 에이전트 모두 반대했습니다. 발의자가 맥락을 취사선택하면 자기에게 유리하게 요약하는 편향이 생기고 직전 맥락을 놓칠 위험이 크다는 이유였습니다. 결국 전체 기록은 그대로 넘기되 발언 자체를 짧게 유지하는 쪽으로 합의했습니다.

## 교차 검증으로 잡아낸 오류들

종료된 108건의 결론을 훑어보니 오류 수정이 기록된 세션이 **11건**, 당장 결론을 내리지 못하고 미결 쟁점으로 남겨 둔 세션이 **26건**이었습니다. 실제로 덕을 본 사례는 크게 세 부류로 나뉩니다.

<CollabCaseCards />

먼저 문서와 실제 코드가 어긋난 경우입니다. WhyNode 기술 개발기 초안을 검토할 때 Gemini가 소스 코드와 대조해 사실 오류 **7건**을 바로잡았습니다. 초안에는 단위 테스트가 "79개"라고 적혀 있었는데 실제로는 오프라인 테스트 74개와 실 API 호출 테스트 5개로 나뉘어 있었고, 스키마를 "다섯 번" 바꿨다는 서술도 확인해 보니 네 차례였습니다. 반대로 왁뿌랩 포트폴리오에서는 Claude가 렌더링 비활성화 CVar 개수가 5종이 아니라 6종이라는 점을 짚어냈고, 뒤이어 Gemini가 버터 상태 머신의 전도 방향이 전방이 아니라 측면이라는 오류를 추가로 찾아냈습니다.

결론은 맞는데 근거가 틀린 사례도 인상적이었습니다. WhyNode를 웹이 아니라 네이티브 앱으로 만들자는 Claude의 권고에 동의하면서, Gemini가 "브라우저에서는 CORS 제약으로 API를 직접 호출할 수 없다"는 이유를 덧붙였습니다. 그러자 Claude가 주요 AI API는 브라우저 직접 호출을 지원한다며 과장된 근거라고 반박했고, Gemini가 이를 인정하고 철회했습니다. 덕분에 최종 근거는 공식 CLI 연동 불가와 Keychain 수준의 인증 정보 보관 불가로 깔끔하게 정리되었습니다. 한쪽이 맞장구치며 보탠 근거까지 다시 걸러지는 장면이었습니다.

눙 언어의 메모리·동시성 모델 명세를 다듬을 때는 경계 조건의 빈틈이 여러 개 드러났습니다. "동시 실행 함수에 공유로 넘긴 값은 완료를 기다리기 전까지 읽기만 허용한다", "취소 확인 지점은 반복의 복귀 지점과 함수 호출 지점으로 둔다" 같은 보완 규칙 **다섯 가지**가 이 과정에서 명세에 추가되었습니다.

## 뜻밖의 수확, 문체 교정 분업

블로그 문서를 함께 쓰다 보니 애초에 의도하지 않았던 분업도 자리 잡았습니다. Claude는 전체 구조와 설계 논리를 잡는 데 강점이 있지만, 한국어 본문을 길게 쓰면 특유의 습관이 배어 나옵니다. "다스립니다", "덜어 냈습니다" 같은 은유나 전문 용어를 일상 동사구로 풀어 쓰는 경향, 질문형·에세이형 제목이 대표적입니다.

WhyNode 문서에서 "힘 기반" 같은 어색한 번역투를 발견해 Gemini에게 전면 재검토를 맡겼더니 **문장 141건**이 교정되어 돌아왔습니다.

<ToneDiffStrip />

이 경험 이후 `project-portfolio` 스킬에 아예 고정 절차를 넣어 두었습니다. Claude가 작성한 한국어 본문은 반드시 Gemini의 교정을 거친다는 원칙입니다. 지금 읽고 계신 이 글 역시 Claude가 108건의 기록을 분석해 초안을 잡고, Gemini가 블로그 문체로 처음부터 다시 쓴 결과물입니다.

## 마치며

6일간의 기록에서 가장 분명하게 확인한 점은, 두 에이전트의 상호 검증이 **코드보다 명세와 문서**에서 효과가 뚜렷하다는 사실입니다. 컴파일러가 잡아 주지 않는 사실 오류, 결론은 맞지만 근거가 흔들리는 주장, 명세의 경계 조건처럼 사람의 눈으로 일일이 대조해야 했던 지점에서 제 몫을 해냈습니다.

앞으로 더 지켜볼 과제는 역시 빠른 합의 편향입니다. 발의자가 응답자의 보완안을 수용하기 전에 한 차례 더 비판적으로 검토하도록 규칙을 넣을지, 지금처럼 빠르게 수렴하는 편이 실용적인지는 기록이 조금 더 쌓인 뒤에 판단하려 합니다.

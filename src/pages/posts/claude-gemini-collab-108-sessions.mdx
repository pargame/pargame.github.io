## 1. 협업 구조

두 에이전트는 같은 스킬 파일을 공유합니다. `~/.claude/skills/collab`과 `~/.gemini/config/skills/collab`이 모두 하나의 설정 저장소를 가리키는 심볼릭 링크이므로, 한쪽에서 수정하면 양쪽에 동시에 반영됩니다.

| 역할 | 수행 내용 |
| :--- | :--- |
| **발의자(A)** | 사용자에게 요청을 받은 에이전트입니다. 자신의 의견을 정리해 상대 CLI를 호출하고, 받은 응답을 사용자에게 보고합니다. |
| **응답자(B)** | 발의자가 호출한 에이전트입니다. 파일을 수정하지 않고 읽기·검색으로만 검증한 뒤, `경로:줄` 근거를 붙여 답합니다. 완전히 동의하면 첫 줄을 `[합의]`로 시작합니다. |
| **사용자** | 보고를 읽고 `.`을 입력해 다음 라운드로 진행하거나, 코멘트를 남겨 다음 의견에 방향을 반영합니다. |

세션은 요청마다 독립된 JSON 파일로 저장되며, 종료 시 최종 결론과 함께 아카이브 디렉터리로 이동합니다. 같은 주제를 이어갈 때는 원문 전체 대신 **요청과 최종 결론만** 새 세션으로 가져옵니다.

<details>
<summary>세션 파일 구조와 명령</summary>

- 저장 위치: 진행 중 `~/.collab/sessions/`, 종료 `~/.collab/archive/`
- 세션 필드: `initiator`, `workdir`, `request`, `inherited`(이어받은 이전 결론), `entries`(`opinion` / `reply` / `note`), `conclusion`
- 명령: `start`, `send`, `note`, `end`, `archive [--here]`, `resume`, `purge [--match] [--sessions] [--yes]`, `status`
- 상대 호출은 9분 타임아웃으로 동작하며, 호출에 실패하면 해당 의견은 기록하지 않습니다. 이때만 CLI 설치·로그인·스킬 경로 같은 사전 요구사항을 진단해 오류 메시지에 덧붙입니다.

</details>

## 2. 스킬 설계와 개선 과정

`collab` 스킬 커밋 12개는 모두 첫날(11월 18일)에 집중되었습니다. 이 개선 대부분이 **스킬 자체를 협업으로 검증한 결과**였습니다. 첫날 세션 18건 중 10건이 스킬 설계와 동작 점검에 쓰였습니다.

| 변경 | 계기 |
| :--- | :--- |
| 보고 형식: `의견 요약 / 인정 / 반박 / 현재 입장` 4단 → `[상대] 원문 + [나] 답변` 대화형 | "너무 딱딱하다"는 사용자 지적. 동의 시에도 반박 칸을 억지로 채워야 하고, 발의자의 요약이 응답자의 원문을 가린다는 문제에 양측 동의 |
| Bash 스크립트 → Python + JSON 저장 | Gemini 검토에서 호출 실패 시 기록 꼬임, 무한 대기, 구분 마커 오작동 위험 지적 |
| 타임아웃 시 프로세스 그룹 종료, 주입된 plan 모드 지침 무시 | 응답자 CLI가 하위 프로세스를 남기거나, 실행 모드 지침 때문에 검증 대신 계획만 세우는 문제 해결 |
| 응답자의 서브에이전트 호출·사용자 질문 금지 | 응답자가 전역 규칙에 따라 사용자에게 질문하려다 멈추는 문제 방지 |
| 근거 `경로:줄` 표기, 인사·재진술 금지 | 매 라운드 전체 기록이 전달되는 구조에서 중복 발언으로 인한 누적 토큰 비용 절감 |

반대로 **기각된 제안**도 있습니다. 매번 전체 기록을 넘기는 대신 전달 범위를 발의자에게 맡기는 방안을 제안했지만, 두 에이전트 모두 검토 끝에 반대했습니다. 발의자가 맥락을 취사선택하면 자신에게 유리하게 요약하는 편향이 생기고 직전 맥락을 누락할 위험이 크다는 이유였습니다. 대신 위 표의 근거 표기 규칙과 재진술 금지로 토큰을 줄이는 쪽으로 합의했습니다.

## 4. 상호 검증으로 잡아낸 주요 사례

종료된 108건의 결론 중 **11건**에 오류 수정이, **26건**에 미결 쟁점이 기록되어 있습니다. 대표적인 사례는 다음과 같습니다.

**사실 오류.** WhyNode 기술 개발기 초안에서는 Gemini가 소스 코드와 대조해 7건을 정정했습니다. 단위 테스트 "79개"는 오프라인 74개와 실 API 호출 5개로 나뉘어 있었고, 스키마 변경 "다섯 번"은 실제로 네 차례였습니다. 왁뿌랩 포트폴리오에서는 반대로 Claude가 렌더링 비활성화 CVar 개수(5종 → 6종)를 바로잡았고, Gemini가 버터 상태 머신의 전도 방향(전방 → 측면)을 추가로 찾아냈습니다.

**잘못된 근거.** WhyNode를 웹이 아닌 네이티브 앱으로 구현하자는 Claude의 권고에 Gemini는 "브라우저에서는 CORS 제약으로 API를 직접 호출할 수 없다"는 근거를 덧붙였습니다. Claude가 주요 AI API는 브라우저 직접 호출을 지원한다며 과장된 근거라고 반박하자 Gemini가 이를 철회했습니다. 최종 근거는 공식 CLI 연동 불가와 Keychain 수준의 인증 정보 보관 불가로 정리되었습니다. 결론은 맞더라도 근거가 틀릴 수 있다는 점을 양방향 검증으로 확인한 사례입니다.

**명세의 빈틈.** 눙 언어의 메모리·동시성 모델 명세에서는 보완 규칙 다섯 가지가 추가되었습니다. "동시 실행 함수에 공유로 넘긴 값은 완료를 기다리기 전까지 읽기만 허용한다", "취소 확인 지점은 반복의 복귀 지점과 함수 호출 지점으로 둔다" 같은 경계 조건들입니다.

## 5. '클로드체'와 문체 교정 분업

블로그 문서를 함께 작성하면서 역할 분담이 자연스럽게 자리 잡았습니다. Claude는 구조와 설계 논리를 잡는 데 강점이 있지만, 한국어 산문에서 특유의 습관이 드러났습니다. "다스립니다", "덜어 냈습니다" 같은 은유, 전문 용어를 일상 동사구로 풀어 쓰는 경향, 질문형·에세이형 제목이 대표적입니다.

WhyNode 문서에서 "힘 기반" 같은 어색한 번역투를 발견해 Gemini에게 전면 재검토를 맡긴 결과, **문장 141건**이 교정되었습니다. "힘 기반 배치"는 "포스 디렉티드 레이아웃"으로, "끌기"는 "드래그"로, "빛"은 "글로우"로 용어가 통일되었습니다.

이 경험은 별도 스킬(`project-portfolio`)의 고정 절차로 자리 잡았습니다. **Claude가 작성한 한국어 본문은 반드시 Gemini의 문체 교정을 거친다**는 원칙이며, 이 글 역시 같은 절차를 밟았습니다.

## 7. 정리

6일간의 기록에서 가장 분명하게 확인한 점은, 두 모델의 상호 검증이 **코드보다 명세와 문서**에서 효과가 크다는 사실입니다. 빌드가 잡아내지 못하는 사실 오류, 결론은 맞지만 근거가 틀린 주장, 명세의 논리적 빈틈이 주로 걸러졌습니다.

남은 과제는 빠른 합의 편향입니다. 발의자가 응답자의 보완안을 수용하기 전에 한 차례 더 비판적으로 검토하도록 강제할지, 지금처럼 빠르게 수렴하는 편이 실용적인지는 기록이 더 쌓인 뒤 판단하려 합니다.

2. 4KB 페이지, 프레임, 페이지 테이블

바이트 단위가 아닌 4KB 덩어리로 주소를 관리하여 매핑 장부의 크기를 최적화하는 기본 단위

// 왜 4KB 단위로 묶어서 관리할까?
• 1바이트마다 변환 주소(8B)를 기록하면 장부 크기가 실제 데이터보다 8배 커집니다!
• 따라서 운영체제와 CPU는 4096바이트(4KB) 단위로 묶어 관리합니다.
• 가상 메모리의 4KB 단위 = 페이지 (Page)
• 물리 RAM의 4KB 단위 = 프레임 (Frame)
💡 페이지 테이블 (Page Table)이란?

"몇 번 가상 페이지(VPN)가 몇 번 물리 프레임(PFN)에 연결되어 있는가?"를 기록해 둔 프로세스별 전용 주소록입니다.

🎯 맥락 닻: 페이지 테이블 항목(PTE) 확인
프로세스 A의 페이지 테이블 (Page Table)
VPN 0x40401 ➔ PFN 0x9A00 (Valid=1)
VPN 0x40402 ➔ PFN 0x1337 (Valid=1)
VPN 0x40403 (현재 타겟) ➔ PFN 0x82F1 (Valid=1)
VPN 0x40404 (미할당 힙) ➔ (연결 없음, Valid=0)

[다음 단계] 또는 [Enter]를 눌러 가상 페이지 번호와 실제 물리 프레임 번호의 매핑 관계를 확인하세요.

3. 주소를 두 조각으로: VPN + 오프셋 (Offset)

가상 주소 변환의 핵심: 하위 12비트는 100% 보존되고, 상위 VPN만 변환된다

// 48비트 가상 주소(VA) 비트 슬라이싱 구조
상위 36비트 [47:12] 하위 12비트 [11:0]
VPN: 0x40403
+ 0xA2C
왜 정확히 12비트일까?
4KB = 4,096 Bytes = 212입니다. 4,096개 바이트 중 몇 번째 바이트인지를 가리키려면 정확히 12비트가 필요합니다.
오프셋 프리셋 테스트:
🎯 맥락 닻: 비트 분해 및 오프셋 보존 원리
1단계: 가상 주소(VA) ➔ VPN + Offset 분해
가상 페이지 번호 (VPN [47:12]) 0x40403
페이지 내부 오프셋 (Offset [11:0]) 0xA2C (2,604번째 바이트)
2단계: 물리 주소(PA) 조립: (PFN << 12) | Offset
물리 프레임 번호 (PFN) 0x82F1 (RAM Frame)
최종 물리 주소 (PA) 0x082F_1A2C

하위 12비트 오프셋(0xA2C)은 변환 없이 그대로 통과하며, 상위 VPN(0x40403)만 페이지 테이블을 거쳐 PFN(0x82F1)으로 바뀝니다.

// MMU 하드웨어 워커 순서 (L0 ➔ L1 ➔ L2 ➔ L3)
💡 왜 4단계로 나눌까? 단일 표로 만들면 236×8B = 512GB의 RAM이 장부로 낭비됩니다!

6. PFN 0x82F1 + 오프셋 조립 완료 PA 확정

5. TLB: 주소 변환 초고속 캐시

매번 4번의 메모리 워크(~240ns)를 하지 않고, 1사이클(~0.25ns) 만에 즉시 변환하는 MMU 내부 캐시

// 연속 메모리 접근 시 TLB 캐시의 기적
1. ldr w0, [x1] (주소 0x4040_3A2C) 첫 접근: Miss
2. ldr w2, [x1, #4] (주소 0x4040_3A30) 인접 접근: Hit!
3. ldr w3, [x5] (주소 0x4040_1A2C) 다른 페이지: Miss
지연 시간 스케일 비교:
• TLB Hit: ~1 사이클 (0.25ns, 파이프라인에 즉시 흡수)
• TLB Miss: 4회 워크 (최악 약 240ns = 1,000배 차이!)
🎯 맥락 닻: TLB 캐시 조회 및 적중률
MMU 내부 TLB (Translation Lookaside Buffer) TLB READY
[Entry 0] VPN: - PFN: - (비어있음)
[Entry 1] VPN: - PFN: - (비어있음)

[다음 단계] 또는 [Enter]를 눌러 첫 Miss 후 TLB에 캐시되고, 다음 접근에서 초고속 Hit가 발생하는 국소성(Locality)을 확인하세요.

7. 권한 비트(PTE)와 Segmentation Fault

하드웨어가 매 접근마다 검사하는 권한 비트와 C++ 개발자가 만나는 SIGSEGV의 실시간 연동

// C++ 버그 시나리오 선택

*ptr = 42; // <-- 0번 가상 주소 접근

Valid (bit0) 0
AP[2] (RO:1) 0
AP[1] (EL0:1) 1

커널 시그널 처리 및 터미널 출력

💡 ARM64 & Apple Silicon 실측 하드웨어 팩트
1. Apple Silicon macOS의 실제 페이지 크기는 16KB입니다.
터미널에서 sysctl hw.pagesize를 실행하면 16384 (16KB)가 출력됩니다. 16KB 그래뉼에서는 오프셋이 14비트 [13:0]이며, 페이지 테이블 1개에 2,048개의 엔트리(11비트)가 들어갑니다. (본 스터디는 리눅스 및 x86의 표준인 4KB를 기준으로 통일하여 설명합니다.)
2. ARM64는 사용자/커널 주소 장부를 하드웨어로 분리합니다.
x86은 CR3 하나로 전체 주소 공간을 관리하지만, ARM64는 하위 절반(사용자)을 TTBR0_EL1, 상위 절반(OS 커널)을 TTBR1_EL1으로 물리적으로 분리합니다. 따라서 컨텍스트 스위칭 시 커널 장부는 건드리지 않고 TTBR0만 교체합니다.
3. ASID (Address Space Identifier)로 TLB 오염 방지
프로세스를 전환할 때마다 TLB 캐시를 전부 비우면 심각한 성능 저하가 발생합니다. ARM64는 각 TLB 엔트리에 8/16비트의 ASID(프로세스 고유 ID 태그)를 붙여 보관하므로, 프로세스가 바뀌어도 TLB를 플러시하지 않고 유지할 수 있습니다.
4. macOS의 __PAGEZERO 보호 세그먼트
macOS의 64비트 Mach-O 바이너리는 하위 4GB(0x0 ~ 0xFFFF_FFFF) 전체를 __PAGEZERO 세그먼트로 지정하고 모든 접근 권한을 0으로 차단합니다. 이를 통해 nullptr 역참조뿐만 아니라 32비트로 잘못 잘린 포인터 접근까지 하드웨어 트랩으로 완벽히 잡아냅니다.

# 내 로그 6,300턴 관찰기: Gemini 3.8 Flash에서 Gemini 4(Argon · Hydrogen · Neon)까지의 에이전트 작업 리듬 변화

**2026. 11. 20** · `#Gemini4` `#AgenticWorkflow` `#LogAnalysis` `#UE5_9`

최근 UE 5.9 곰팡이 프로젝트([곰팡이 우주 정복 대작전](/learn/projects/fungal-space-conquest))를 마무리하고 블로그를 정리하면서, 로컬 에이전트 환경(Antigravity CLI)에서 **Gemini 3.8 Flash**에서 **Gemini 4 계열(Argon · Hydrogen · Neon)**으로 자연스럽게 넘어오게 되었습니다.

체감상 "예전 Flash보다 한 턴은 조금 묵직한데, 이상하게 큰 작업은 더 빨리 끝난다"는 느낌이 들었습니다. 감으로만 남기기 아쉬워 로컬에 쌓여 있던 실제 대화 로그(`transcript.jsonl`) 102개, 총 **6,367개의 에이전트 응답 턴**을 직접 집계해 보았습니다.

> 이 글은 통제된 조건에서 모델 자체의 성능을 겨루는 **벤치마크가 아닙니다.** 실제 개발 과정에서 쌓인 내 로그를 기반으로, **에이전트가 도구를 다루는 방식과 1스텝 왕복 리듬이 어떻게 달라졌는지** 정리한 관찰 기록입니다.

## 1. 데이터 출처와 측정 정의

로컬 `~/.gemini/antigravity-cli/brain/*/.system_generated/logs/transcript.jsonl` 102개 파일(2026. 09. 08 ~ 2026. 11. 20)을 대상으로 분석했습니다.

* **전체 응답 턴 (`PLANNER_RESPONSE`)**: 총 **6,367턴**
  * 모델 라벨을 확인할 수 없는 **미상 구간 762턴**과 타사 모델(Claude 등) 턴은 별도로 제외했습니다.
* **측정 지표 — "추론 속도"가 아닌 "에이전트 1스텝 왕복 시간"**:
  * 로그의 `PLANNER_RESPONSE.created_at`은 응답 완료 시각이 아니라 **생성을 시작한 시각**입니다.
  * 따라서 `다음 스텝 시각 - PLANNER_RESPONSE 시각`에는 **모델 생성(thinking 포함) + 도구 실행 + 오케스트레이션 오버헤드**가 모두 섞여 있습니다.
  * 사용자 입력을 기다리는 `ask_question` 턴과 `USER_INPUT`으로 넘어가는 구간은 왜곡을 막기 위해 제외했고, 타임스탬프 해상도가 1초 단위이므로 중앙값·P90은 소수 첫째 자리(사실상 초 단위)까지만 표기했습니다.

## 3. 모델 · Thinking 레벨 · 도구 종류별 1스텝 왕복 시간

모델마다 Thinking 레벨(`High` / `Medium`) 비중과 주로 호출한 도구가 다르므로, 전체 스텝과 함께 **파일 읽기·편집 전용 스텝(`read_file` / `edit_file` / `write_file`)**과 **셸 명령 스텝(`run_command`)**을 층화해 비교했습니다.

| 모델 (Thinking 레벨) | 세션 수 (최대 세션 비중) | 전체 도구 스텝 (중앙값 / P90) | 파일 읽기·편집만 (중앙값 / P90) | `run_command` (중앙값 / P90) |
| :--- | :---: | :---: | :---: | :---: |
| **Gemini 3.8 Flash (High)** | 30개 (17%) | **5s** / 12s | **5s** / 15s | **5s** / 11s |
| **Gemini 3.8 Flash (Medium)** | 20개 (33%) | **5s** / 18s | **5s** / 24s | **5s** / 9s |
| **Gemini 4 Argon (High)** | 5개 (70%) | **11s** / 31s | **11.5s** / 31s | **11s** / 31s |
| **Gemini 4 Argon (Medium)** | 8개 (60%) | **10s** / 25s | **10s** / 35s | **10s** / 22s |
| **Gemini 4 Hydrogen (Medium)** | 11개 (92%) | **6s** / **10s** | **6s** / **11s** | **5s** / **10s** |
| **Gemini 4 Neon (Medium)** | 3개 (82%) | **9s** / 20s | **8s** / 17s | **10s** / 20s |

관찰된 특징을 정리하면 다음과 같습니다.

1. **단일 스텝 응답의 즉각성**: `3.8 Flash`는 중앙값 **5초**로 단일 턴 반응이 가장 짧았습니다.
2. **꼬리 지연(P90)의 안정성**: `4 Hydrogen (Medium)`은 중앙값 **6초**, P90 **10~11초**로, 단일 스텝이 유독 길게 늘어지는 구간이 가장 적었습니다. 곰팡이 프로젝트 핵심 개발과 자소서·문서 정리가 몰렸던 장시간 세션(`c12b7e7f`)에서 리듬이 끊기지 않았던 이유와 일치합니다.
3. **묵직한 추론과 병렬 처리의 절충**: `4 Neon (Medium)`은 파일 읽기·편집 스텝 중앙값이 **8초**(P90 17초)로 `3.8 Flash`(5초)보다 턴당 시간은 길지만, 한 턴에 평균 **2.08개** 도구를 묶어 실행하기 때문에 여러 파일을 동시에 고치는 작업에서는 왕복 횟수 자체가 절반 가까이 줄어듭니다.
4. **가장 무거운 구간**: `4 Argon`은 `Medium`(10초 / P90 25초)과 `High`(11초 / P90 31초) 모두 가장 묵직한 왕복 시간을 보였습니다.

## 4. 도구 구성 차이로 본 실제 작업 맥락

같은 "개발 로그"라도 모델마다 맡았던 작업 성격이 달랐습니다.

| 모델 | 상위 3개 호출 도구 | 주로 투입된 작업 맥락 |
| :--- | :--- | :--- |
| **3.8 Flash (High)** | `run_command`(1,557), `read_file`(357), `edit_file`(165) | 터미널 기반 환경 점검, 초기 블로그·슬라이드·툴체인 조사 |
| **4 Argon (High)** | `run_command`(121), `read_file`(74), `edit_file`(22) | UE 5.9 macOS 호환성·툴체인 심층 조사 및 설계 검증 |
| **4 Hydrogen (Medium)** | `run_command`(106), `edit_file`(58), `read_file`(55) | 곰팡이 프로젝트 C++ 구현·최적화 및 문서 작성 |
| **4 Neon (Medium)** | `edit_file`(309), `run_command`(166), `read_file`(146) | 곰팡이 포트폴리오 마무리, 블로그 3단 구조 리팩터링, Notion MCP 기획서 연동 |

`3.8 Flash (High)`는 셸 명령 비중이 압도적으로 높았고, `4 Neon (Medium)`은 다중 파일 편집(`edit_file`)과 MCP 도구 호출 비중이 높았습니다. 즉, 위 표의 시간 차이에는 모델 특성뿐 아니라 **수행한 작업의 종류**도 함께 반영되어 있습니다.

## 5. 이 데이터를 읽을 때 반드시 감안해야 할 한계

이번 집계는 Claude와의 교차 검증을 거쳐 아래 네 가지 한계를 명확히 확인하고 기록합니다.

1. **세션 표본 편중**: `Hydrogen` 턴의 **92%**가 단일 세션(`c12b7e7f`), `Neon` 턴의 **82%**가 단일 세션(`8c88f390`), `Argon (High)`의 **70%**가 단일 세션(`8b64bf51`)에서 나왔습니다. 턴 수는 수백 개지만 독립된 세션 단위로 보면 `n = 1~3` 수준이므로 일반화된 성능 순위로 해석해서는 안 됩니다.
2. **하네스 · 프롬프트 변화의 교란**: `3.8 Flash`(9~11월 초)에서 `Gemini 4`(11월 중순)로 넘어오는 사이, 에이전트 시스템 프롬프트에 병렬 배치 호출을 강하게 권장하는 지침이 강화되었습니다. 병렬 배치율 급증(1% → 40%)은 모델 능력 향상과 하네스 변화가 **함께 작용한 결과**로 보는 것이 타당합니다.
3. **도구 실행 시간 혼입**: 1스텝 왕복 시간에는 빌드(`astro build`, UBT), 웹 검색, MCP 네트워크 왕복 시간이 포함되어 있어 순수 토큰 생성 속도(TPS)와 동일하지 않습니다.
4. **미상 구간(762턴)**: 초기 로그 일부에 모델 필드가 기록되지 않아 집계에서 제외했습니다.

## 6. 실전 체감 정리

로그를 직접 까보고 나서야 체감의 정체가 선명해졌습니다.

* **체감 작업 속도는 "한 턴이 몇 초인가"만으로 결정되지 않습니다.** `3.8 Flash`처럼 5초 만에 답이 와도 매번 파일 하나씩만 열어보면 10턴을 왕복하게 되고, `4 Neon`처럼 8~9초가 걸려도 한 턴에 파일 3~4개를 동시에 읽고 편집하면 전체 작업 흐름이 훨씬 매끄럽게 느껴집니다.
* **`4 Hydrogen`은 빠른 템포(중앙값 6s, P90 10s)와 적당한 병렬성(25%)의 균형**이 좋아 긴 구현 세션에서 기다리는 피로도가 가장 적었고, **`4 Neon`은 다중 파일 편집과 리팩터링(병렬 배치율 40.3%)**에서 강점이 뚜렷했습니다.

앞으로도 모델이 바뀔 때마다 감상평에 그치지 않고, 실제 작업 로그를 기준으로 에이전트 워크플로우의 변화를 계속 기록해 나갈 예정입니다.

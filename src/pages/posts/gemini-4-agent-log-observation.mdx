## 2. 파일 작업 한 스텝은 얼마나 걸리나? (중앙값과 P90)

로그의 `PLANNER_RESPONSE.created_at`은 생성 시작 시각입니다. 따라서 다음 스텝까지의 간격은 순수 추론 시간이 아니라 **생성(thinking 포함) + 도구 실행이 합쳐진 1스텝 왕복 시간**입니다.

실행 시간 편차가 큰 `run_command`와 사용자 대기가 섞이는 `ask_question`은 제외했습니다. <strong>파일 읽기·편집 전용 스텝(<code>read_file</code> / <code>edit_file</code> / <code>write_file</code>)</strong>만 0~40초 같은 선형 축에 올렸습니다.

## 5. 결론: 숫자가 말해 주는 에이전트 작업 리듬의 구조

도입부의 질문으로 돌아가 봅시다. *스텝 중앙값은 3.8 Flash가 가장 짧았는데, 왜 Gemini 4 쪽이 덜 기다린다고 느껴졌을까요?* 세 차트와 도구 종류별 단일·병렬 분해 데이터를 함께 보면 세 가지 구조적 이유가 드러납니다.

### 5.1. 병렬 호출의 이득은 '읽기'와 '편집'에서 다르게 작동한다

같은 모델 안에서 **읽기 전용 스텝**과 **편집 전용 스텝**을 분리해 단일 호출(1개)과 병렬 호출(2개 이상)의 소요 시간을 다시 비교해 보았습니다.

| 모델 | 읽기 단일 중앙값 | 읽기 병렬 (중앙값 · 도구당) | 편집 단일 중앙값 | 편집 병렬 (중앙값 · 도구당) |
| :--- | :---: | :---: | :---: | :---: |
| **Gemini 3.8 Flash** | 4초 (`n=841`) | 4초 · **2.0초/개** (`n=10`) | 8초 (`n=393`) | 12초 · 6.0초/개 (`n=3`) |
| **Gemini 4 Argon** | 9초 (`n=77`) | 9초 · **4.0초/개** (`n=23`) | 21.5초 (`n=46`) | 12초 · 6.0초/개 (`n=7`) |
| **Gemini 4 Hydrogen** | 4초 (`n=21`) | 4초 · **2.0초/개** (`n=11`) | 7초 (`n=46`) | 5초 · 2.4초/개 (`n=8`) |
| **Gemini 4 Neon** | 7초 (`n=51`) | 6초 · **2.7초/개** (`n=25`) | 11초 (`n=5`) | 12초 · **2.6초/개** (`n=62`, 평균 5.1개) |

* **읽기 작업(입력 위주)은 병렬 상각 효과가 매우 크다**: 파일 경로와 줄 번호만 넘기면 되므로 출력 토큰이 거의 늘지 않습니다. 실제로 4개 모델 모두 2~3개 파일을 한 턴에 묶어 읽어도 스텝 중앙값이 단일 호출과 같거나 1초 이내 차이였습니다(Flash 4초→4초, Hydrogen 4초→4초, Argon 9초→9초, Neon 7초→6초). 매 턴 발생하는 <strong>고정 왕복 비용(누적 컨텍스트 재전송 + 추론 시작 지연)</strong>이 도구 개수만큼 그대로 분산됩니다.
* **편집 작업(출력 위주)은 생성 토큰 비용이 함께 늘지만 아선형(sub-linear)이다**: 수정할 코드 본문을 생성해야 하므로 편집 스텝은 읽기(4~9초)보다 원래 길게 걸립니다. 다만 여러 편집을 한 턴에 묶어도 턴 시간이 호출 수만큼 선형으로 늘어나지 않아 도구 1개당 시간은 줄어듭니다(예: `4 Neon` 병렬 편집 62턴은 평균 5.1개 편집을 12초 중앙값, 도구당 2.6초로 처리).

### 5.2. 작업 흐름을 끊는 것은 중앙값이 아니라 꼬리 지연(P90)이다

파일 작업 스텝의 중앙값은 모든 모델이 5~11.5초 사이에 모여 있습니다. 반면 10번 중 1번 찾아오는 **P90 꼬리 지연**은 모델마다 11초에서 35초까지 3배 넘게 벌어졌습니다.

사람이 에이전트와 협업할 때 5초와 6초의 차이는 거의 의식하지 못하지만, 작업 도중 25~35초씩 멈추는 턴이 반복되면 집중 흐름이 끊어집니다. <strong><code>4 Hydrogen (Medium)</code></strong>이 이번 로그에서 가장 일관된 구간(중앙값 6초 · P90 11초)을 보인 점이 체감 리듬에 크게 작용했을 가능성이 높습니다(단, `n=86`, 단일 세션 비중 92% 전제).

### 5.3. 모델, 하네스, 작업 성격이 맞물린 관찰 정리

4장에서 밝혔듯 이번 로그는 통제된 벤치마크가 아니라 실제 프로젝트에 각 모델을 투입한 기록입니다. 모델 우열을 단정하기보다, **맡긴 작업과 관찰된 리듬**으로 정리하면 다음과 같습니다.

* <strong><code>4 Hydrogen (Medium)</code></strong> — 곰팡이 프로젝트 C++ 구현과 문서 작성에 집중 투입. 중앙값 6초 · P90 11초의 좁은 왕복 구간과 24.9% 병렬 배치가 관찰됨.
* <strong><code>4 Neon (Medium)</code></strong> — 블로그 3단 구조 리팩터링과 Notion MCP 일괄 작업에 투입. 다중 편집 비중(41.2%)이 높은 작업 특성상 40.3% 병렬 배치(병렬 편집 시 평균 5.1개/턴)가 두드러짐.
* <strong><code>3.8 Flash</code></strong> — 초기 터미널 점검·빌드(셸 61.2%)와 단발성 조사 위주. 중앙값 5초로 빠르지만 거의 1턴 1도구 순차 호출.
* <strong><code>4 Argon</code></strong> — UE 5.9 호환성·툴체인 심층 조사에 투입. 중앙값 10~11.5초, P90 31~35초로 스텝당 호흡이 가장 길었음.

결국 에이전트 코딩에서 체감 속도를 결정하는 것은 단일 모델의 토큰 생성 속도만이 아닙니다. <strong>독립된 읽기·편집을 한 턴에 묶어 고정 왕복 비용을 줄이는 워크플로우(모델 능력 + 하네스 지침)</strong>와 **꼬리 지연을 관리하는 세션 운영**이 함께 맞물릴 때 작업 리듬이 눈에 띄게 달라집니다.

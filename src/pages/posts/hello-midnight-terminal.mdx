# 블로그 리뉴얼: Astro 스캐폴딩 설계와 모던 정적 아키텍처 구현기

기존의 무겁고 제한적이었던 블로그 프레임워크를 걷어내고, 개인 엔지니어링 스터디 아카이브인 **pargame.github.io**를 처음부터 직접 설계하여 구축했습니다.

Gemini Pro와의 페어 프로그래밍 및 멀티 에이전트 교차 검증을 통해, 단순한 템플릿 사용을 배제하고 **왜 이 스택을 선택했고 각 레이어를 어떻게 코딩했는지**에 대한 기술적 결정과 구현 내역을 기록합니다.

---

## 1. 프레임워크 선정: 왜 Next.js가 아닌 Astro인가?

리액트 생태계의 Next.js나 개츠비(Gatsby) 같은 전통적인 SPA 기반 정적 생성기는 심각한 한계가 있었습니다.

* **불필요한 하이드레이션(Hydration) 비용**: 아무리 SSG로 정적 HTML을 뽑아내도, 브라우저가 화면을 띄운 뒤 전체 React 런타임 번들을 내려받아 DOM 트리를 전수 검사하고 이벤트 리스너를 재부착합니다. 단순 텍스트와 코드를 읽는 데 수백 KB의 JS 파싱 오버헤드가 발생합니다.
* **Astro의 0KB JS 코어**: Astro는 템플릿과 마크다운, 레이아웃을 빌드 시점에 **순수 HTML과 CSS**로만 컴파일합니다. 클라이언트에 전송되는 기본 자바스크립트는 0KB입니다.
* **Islands 아키텍처의 격리 실행**: 향후 C++ 메모리 시뮬레이터나 Pyodide(WebAssembly) 기반 파이썬 REPL 같은 무거운 동적 컴포넌트가 필요할 때만, `@astrojs/react`를 통해 해당 위젯만 독립된 섬(Island)으로 띄우고 `client:visible`로 지연 로딩할 수 있습니다.

## 2. 블로그 스캐폴딩의 핵심 구현 기술

이번에 구축한 프로젝트 템플릿 코드의 핵심 설계 내역입니다.

### ① Zero-FOIT (무깜빡임) 인라인 테마 인젝터
리액트 `useEffect`나 외부 스크립트로 다크 모드를 제어하면, 브라우저가 흰 배경을 먼저 렌더링한 후 다크 모드로 전환되면서 화면이 번쩍이는 **FOIT(Flash of Inaccurate Theme)** 현상이 발생합니다.

이를 완벽히 차단하기 위해 `src/layouts/BaseLayout.astro`의 `<head>` 최상단에 **동기식 인라인 자바스크립트(`script is:inline`)**를 배치했습니다:

```html
<!-- BaseLayout.astro: First Paint 이전 동기 실행 -->
<script is:inline>
  const theme = (() => {
    if (typeof localStorage !== 'undefined' && localStorage.getItem('theme')) {
      return localStorage.getItem('theme');
    }
    return window.matchMedia('(prefers-color-scheme: light)').matches ? 'light' : 'dark';
  })();
  document.documentElement.setAttribute('data-theme', theme);
</script>
```

브라우저 렌더러가 DOM 파싱을 시작하기 전, `localStorage`와 OS의 미디어 쿼리를 즉시 평가하여 `<html>` 태그에 `data-theme`을 주입하므로 깜빡임이 0ms로 억제됩니다.

### ② CSS Custom Properties (HSL) 기반의 Midnight Terminal 시스템
TailwindCSS 같은 유틸리티 프레임워크 대신 순수 Vanilla CSS 커스텀 프로퍼티를 선택했습니다.
* **선정이유**: 런타임 및 빌드 도구 종속성을 배제하고, CSS 변수만으로 테마 전환을 0ms에 처리하기 위함입니다.
* **명도 대비 최적화**: 딥 인디고 블랙(`hsl(232, 28%, 7%)`)을 베이스로 두고, 본문 텍스트(`hsl(228, 14%, 76%)`)와의 명도 대비비를 **11:1**(WCAG AAA 기준 초과 달성)로 맞춰 장시간 코드 분석 시의 눈 피로도를 낮췄습니다.
* **독서 인체공학 규격**: 가독성 최적 본문 폭(`--measure: 68ch`), 한글 단어 끊김 방지(`word-break: keep-all`), 행간(`--lh-body: 1.8`)을 전역 정의했습니다.

### ③ Shiki 듀얼 테마 빌드 타임 렌더링
클라이언트 사이드에서 Prism이나 Highlight.js를 돌리면 무거운 구문 분석 정규식이 브라우저 메인 스레드를 점유합니다.
* Astro의 내장 Shiki 엔진을 활용하여 **빌드 타임에 정적 HTML 토큰으로 변환**했습니다.
* 다크(`tokyo-night`)와 라이트(`github-light`) 구문 강조 색상을 CSS 변수(`--shiki-dark`, `--shiki-light`)로 동시에 출력하여, 테마 전환 시 자바스크립트 재실행 없이 CSS 변수 스왑만으로 즉시 코드 테마가 전환됩니다.

### ④ GitHub Actions OIDC 기반 공식 배포 파이프라인
과거의 `gh-pages` 브랜치 커밋 방식은 빌드 번들 파일들이 git 히스토리를 오염시키는 문제가 있었습니다.
* `permissions: pages: write, id-token: write`를 명시하고,
* `actions/upload-pages-artifact@v3`와 `actions/deploy-pages@v4`를 결합하여 번들 산출물을 브랜치 커밋 없이 GitHub Pages 인프라에 직접 원자적(atomic) 배포하도록 구성했습니다:

```yaml
# .github/workflows/deploy.yml
permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 26, cache: npm }
      - run: npm ci && npm run build
      - uses: actions/upload-pages-artifact@v3
        with: { path: './dist' }

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/deploy-pages@v4
```

### ⑤ 데이터 기반 스터디 아카이브 구조
스터디 주제가 늘어날 때마다 프론트엔드 라우트나 컴포넌트를 매번 수정하지 않도록, `src/data/tracks.json`을 단일 진실 공급원(SSOT)으로 삼았습니다.
* Foundations (C++, Core CS)
* Systems (동시성, 네트워크, DB)
* Game Engine (언리얼 엔진)

새 카테고리를 공부할 때는 JSON 데이터와 마크다운 파일만 추가하면 메인 화면 카드, 사이드바, 검색 인덱스가 자동으로 동기화됩니다.

---

## 3. 결론

이번 스캐폴딩의 핵심은 **"읽는 경험은 극한으로 가볍게(0KB JS), 엔지니어링 실험은 완전히 유연하게(Islands), 배포는 클라우드 파이프라인으로 투명하게"** 만드는 것이었습니다.

이제 세팅된 환경 위에서 C++, 동시성, 네트워크, 언리얼, nung_lang 등을 깊이 있게 파고들며 스터디 기록을 축적해 나갈 것입니다.
